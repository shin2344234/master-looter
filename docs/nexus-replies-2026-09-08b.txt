[b]Fyreon87[/b] Ninety minutes of load order elimination is a lot to ask of

You have put me in the right area. Flipping frame generation destroys the

swapchain, so it is doing graphics work on an object that is being pulled out
from under it. That is my problem to fix.

Since you posted I have had it reproducing on a borrowed 5060 Ti, which is
further than I expected to get today, and I can tell you what it looks like
from the inside.

The game dies with two null pointer reads in its own code, a few milliseconds

assumes it cannot be on the path that dies. Something it looks for during the
switch is not there, and it is only not there when my mod is loaded.

The mod puts exactly one thing in that path. It wraps the swapchain so the menu
can draw before frame generation interpolates. My working theory is that
handing the game my object instead of the real one makes a lookup miss and
hand back nothing.

Two things from you would help, and neither is urgent.

[b]The log from a run that crashed.[/b] MasterLooter.log in bin64, and
MasterLooter.01.log next to it, which holds the run before that one.

[b]Which frame generation.[/b] The game's own, DLSS, FSR, or something like

the machine I borrowed may not be running the same one you are.

I am not going to ask you to set wrapSwapChain=0, which is what I was about to

crashing and we would both have been fooled. That is fixed in the next build,
which also stops the mod going quiet when it cannot draw.

Nothing here can damage a save.

REPLY 3 -- to jacksterson, Proton
=============================================================================

[b]jacksterson[/b] No log file at all settles more than you might expect. The
log is opened the moment the DLL loads, well before anything gets drawn, so a
plugin that started and then died still leaves the file behind. Yours never
reached that point.

Which means the mod is not what is stopping your game. Something further
upstream is keeping it from being loaded at all, and that is a different
problem with a different fix.

Your overrides look right to me. winmm=n,b is the one that matters and you have
it. Two things I would check, in this order:

[b]1.[/b] Is MasterLooter.asi sitting in bin64 inside the prefix, next to
winmm.dll? A mod manager working through a Windows-shaped path can end up
writing somewhere the prefix never looks.

[b]2.[/b] Does the game start with winmm.dll present and MasterLooter.asi
deleted? That tells us whether the loader is unhappy with your configuration
generally or whether this plugin specifically is what kills it. If the game is
fine without the .asi and dies with it, then the plugin is getting far enough
to take the process down before it can open its own log, and I would start
looking at the byte pattern scan or at the Direct3D hook meeting DXVK instead
of real D3D12.

One thing I noticed: you are overriding dxgi as well, for RenoDX. This mod
hooks the DXGI present path too. Two things reaching for it under DXVK is a
plausible way to lose a process without a word, though I want to be clear that
is where I would look next and not a diagnosis.

There is no Linux machine here, so I am relying on you for anything past this.
Issue #15 has everything so far.

REPLY 4 -- to LuxDragon, filtering individual creatures
=============================================================================

[b]LuxDragon[/b] This is #29 now, so it is out of my head and somewhere I will
actually see it.

Where it really stands: items already answer to three levels of control, per
item, per tag and per class. Creatures answer to none of them. They get
recognised by their model and sorted by a pair of category bytes, so unlike an
item they have no stable name for a rule to attach to. Giving them one is the
whole job. The interface to hang it off has been there since 1.2.0.
